# Part B — phase3_015 iter5 root-cause (HIGH PRIORITY)

### The trace (all values verified from artifacts)

State entering iter5, read from the iter4 commit `f14d0ab:runs/_summary/phase3_015_state.json`:

```
set_id=3  set_phase=refine  set_best_cer=0.18735514  set_best_hyp_id=phase3_015_iter_004
set_refines_used=0  best_cer=0.17573149  evaluated_count=3
```

State after iter5, from the iter5 commit `05116da:...state.json` — **byte-identical in every set field**:

```
set_id=3  set_phase=refine  set_best_cer=0.18735514  set_refines_used=0  evaluated_count=3
```

The displayed decision (`runs/_summary/phase3_015_decisions.jsonl`, iter 5):

```
final_decision=micro_bank  attempt_status=evaluated  cer=0.17628914
decision_reason="axis improved: error_breakdown.del_ratio 0.324634 < 0.363150"
override=set:refine  chosen_mode=refine
portfolio_slots_updated=[metric_best:best_deletion, metric_best:best_low_hallucination, micro_bank, near_best]
```

But `runs/_summary/HISTORY.md`, iter 5 entry, records what the runner *actually* returned:

```
## iter 5 · phase3_015_iter_005 · cer=NA (ΔNA) · reject
### 분석
verify 중 scope 위반: docs/superpowers/plans/2026-06-05-phase1.5-metadata-off-git.md
```

### What actually happened

iter5 hit the **post-verify scope-violation branch** at `harness/runner.py:2070-2095`. During verify the candidate's `transcribe` produced a valid `score_report.json` (cer 0.17628, runtime 214s — within budget), but `git_status` afterward saw an **untracked, unrelated file** — `docs/superpowers/plans/2026-06-05-phase1.5-metadata-off-git.md` (the plan doc itself; it was untracked in the worktree during the 12:5x run and only committed later at `731f268`). `disallowed_post_verify_paths` (`runner.py:318`) flags any non-`allowed_path`, non-`runs/<hyp>/` path, so it returned that doc as a violation.

The post-verify reject branch (`runner.py:2073`) then returns immediately with `status="reject"`. Critically, this branch:

- is **before** `state.record_evaluated()` (`runner.py:2170`) → `evaluated_count` stays 3 ✓ (matches data);
- is **before** the entire set scored-decision block (`runner.py:2214-2280`) → `decide_lineage_progress` / `step_set` / `_persist_set_state` are **never called** → the set state is untouched ✓ (matches the byte-identical before/after);
- passes `decision_status="reject"` to `commit_iteration`.

The misleading `micro_bank` label is produced **independently of control flow** by `_persist_decision` (`runner.py:1739-1747, 1768-1804`): it re-reads the iter dir's `score_report.json` off disk (`runner.py:1672-1678`). Because the file exists, it sets `attempt_status="evaluated"` (`runner.py:1769-1770`) and — since `status=="reject"` and a report is present — runs `is_micro_bank`, which finds an axis improvement (iter5 `del_ratio` 0.324634 < global_best iter3 0.363150 — both verified from the score_reports) and rewrites the *displayed* `final_decision` to `micro_bank` with that axis reason. The runner's true `result.reason` (the scope violation) only survives in `HISTORY.md`.

### Confirming the set-path logic is correct (throwaway repro, since deleted)

With the EXPECTED inputs the set path would have done the right thing:

```
decide_lineage_progress(cer=0.17628, lineage_best=0.18735) -> advance  ("lineage improvement Δ0.011066")
decide_promotion(0.17628 vs champion 0.17573)             -> reject    (Δ -0.000558 < keep_delta_eps)
step_set(refine, advance, beats_champion=False)           -> action=advance, best_cer=0.17628, refines_used=1
```

So **had iter5 reached the set path, it would have advanced** exactly as the bug report expected. It did not reach it. The hypotheses in the brief are all refuted:

- `lineage_best_cer` IS passed as `state.set_best_cer` (`runner.py:2225`) — correct.
- `_set_state_from`/`_persist_set_state` round-trip `set_best_cer`/`set_refines_used` correctly (verified by the iter4 commit state and the repro).
- The resume reconstructed `set_best_cer=0.18735` correctly (iter4 commit state confirms).
- No off-by-one and no `advance→reject` mapping in `step_set`.
- The decisive cause: iter5 **did not enter the set scored path at all** — the post-verify scope guard returned first.

### Verdict

**Not the set-path bug under investigation.** iter5 is a false-positive scope rejection — the **same over-broad guard** that phase1.5's brief attributes to iter6. The set/lineage code (`decide_lineage_progress`, `step_set`, `_set_state_from`, `_persist_set_state`, the scored-path mapping) is **correct**; no change is warranted there.

**The real defect** (already in scope of phase1.5) is twofold:

1. **`disallowed_post_verify_paths` + `candidate_owned_statuses` are repo-wide.** An untracked file the candidate never touched (the plan doc) is treated as a candidate scope violation and rejects an otherwise-promotable iteration. Worse, `candidate_owned_statuses` (`runner.py:367`, the `parts[:1] != ("runs",)` clause) **owns** that doc, so `rollback_paths` → `git clean -fd` (`runner.py:364`) would have *deleted* it had it not been committed in time. This is the exact collateral-damage hazard phase1.5 Task 2 targets — and the iter5 evidence is real-world proof it fires.
   - *Fix (already in phase1.5):* the post-verify guard must scope to the candidate's actual writes, and rollback must never `git clean` unrelated untracked paths. Note phase1.5 as currently written narrows **rollback/ownership** but does **not** narrow **detection** (`disallowed_post_verify_paths` still flags any stray untracked file). **A bare untracked operator/scratch file in the repo root would STILL reject the iteration** under phase1.5. See phase1.5 Important #2.

2. **`_persist_decision` overwrites the runner's true outcome label** (`runner.py:1768-1804`): a scope-rejected iter with a leftover `score_report.json` is shown as `micro_bank/evaluated`, masking the rejection in `decisions.jsonl`. This is a diagnostics-integrity bug — the operator reading `decisions.jsonl` cannot see that iter5 was a scope reject. (Out of scope of both plans; flagged as a follow-up below.)

**Exact fix locations:** detection precision at `harness/runner.py:318` (`disallowed_post_verify_paths`) and `:2068-2069`; rollback precision at `:356-364` / `:367-376`; label-integrity at `:1768-1785` (skip `is_micro_bank` / force `evaluated`-vs-reject consistency when the caller passed `status="reject"` with a non-`evaluated` reason). The first two are covered by phase1.5 (with the gap noted); the third should be a small standalone fix.

# Part A — Plan reviews

## Plan 1 — Phase 1.5 (metadata off git) — **ready-with-fixes**

### Strengths

- **Grounding is accurate.** Every cited anchor checks out against current code: `GitPathStatus`/`untracked` (`runner.py:273-279`), `git_status` (`:292`), `rollback_paths` (`:356`), `candidate_owned_statuses` (`:367`, and the quoted body with the `parts[:1] != ("runs",)` clause is verbatim), `commit_iteration` (`:1826`), `run_job` abort branches (`:2311/2335/2359`), `_init_repo` gitignore (`tests/test_harness_runner.py:76-79`) and its `git add` of `runs/_summary/HISTORY.md` (`:100-101`). `.gitignore` is indeed `runs/*` + `!runs/_summary/` (lines 19-20).
- **The core design is sound and the ordering discipline is correct.** Landing detection precision (Tasks 1-2) *before* the `.gitignore` flip (Task 3-4) means there is never a window where poison under an ignored `runs/` is invisible. Good.
- **`git status --porcelain -uall --ignored` per-path claim is correct.** With `-uall`, `--ignored` lists ignored files individually (code `!!`) instead of collapsing to a directory line — so a candidate write into an ignored `runs/_summary/<job>_state.json` IS detected. The empirical verification block is right.
- **The collateral-delete diagnosis is real and now independently confirmed** by Part B: iter5/iter6 of phase3_015 show the over-broad `candidate_owned_statuses` ownership of an unrelated `docs/...` file. Removing the `parts[:1] != ("runs",)` clause is the right call and does not widen the allow-list.
- **TDD completeness is high** — every task has a failing test, an implement step, a pass step, real code (no placeholders), and the self-review's spec-coverage table maps each design decision to a task.
- **The D4 `reset`-restore subtlety is handled correctly.** The plan correctly identifies that `restore_file_from_ref(champion)` on `reset` leaves `workspace/transcribe.py` differing from the job-branch HEAD (a tracked-modified file), which would trip the next `ensure_worktree_ready`, and therefore makes `reset` a code-checkpoint status that commits. This is the right minimal resolution.

### Issues

**Critical**

- **C1 — Detection is NOT narrowed; only ownership/rollback is. The iter5-class false-positive scope reject survives phase1.5.** (Plan D1 / Task 1 / Task 3; code `runner.py:318` `disallowed_post_verify_paths`, `:306` `disallowed_candidate_paths`.) The plan makes `candidate_owned_statuses` precise and replaces `git clean` with a precise fs-delete — good for *collateral deletion*. But `disallowed_post_verify_paths`/`disallowed_candidate_paths` still flag **any** path that is not `allowed_path` / not `runs/<hyp>/`, and Task 1 *adds ignored paths to that visibility*. So after phase1.5, a stray untracked file anywhere (an operator scratch file, an uncommitted doc — exactly the iter5 `docs/...plan.md`) **still rejects the iteration as a scope violation**. The plan's own `test_scope_violation_removes_poison_outside_owned_surface` even asserts the reject still happens. The collateral *deletion* is fixed; the spurious *rejection* is not.
  - *Why it matters:* the headline real-world failure (a promotable iter5 thrown away because an unrelated untracked file existed) would recur under phase1.5.
  - *Fix:* decide the intended contract explicitly. Either (a) detection should also ignore non-candidate untracked paths that pre-existed the candidate run (snapshot the pre-candidate `git_status` and diff — only NEW paths the candidate created are violations), or (b) keep rejecting on stray files but document that the operator must keep the worktree clean. (a) is the behavior the iter5 evidence argues for. The plan should state which, and add a test: "an untracked operator file present before the candidate runs does NOT cause a scope reject." As written the plan silently chooses (b), which contradicts the motivating hazard.

**Important**

- **I1 — `commit_iteration` signature drift on the `reset` status.** (Task 4 Step 5-6.) The plan introduces a new commit status `"reset"` and a non-committing `"repair_rollback"`, and changes the set verify-fail and scored branches to pass them. But the **legacy single-shot path** (`runner.py:2207-2211`) and the four `run_job` abort calls still pass `"abort"`/`decision.status`. The plan handles those (abort removed in Task 5, legacy `reject`→no-op), but `_CODE_CHECKPOINT_STATUSES = ("keep","success","lineage_advance","reset")` must be the single source of truth and every `commit_iteration` caller's status string must be in or out of that set deliberately. Add an assertion/test enumerating all caller statuses so a future status string can't silently start (or stop) committing. Currently the mapping lives implicitly across ~6 call sites.
- **I2 — `IterationResult.status` vs commit status decoupling needs a test, not just prose.** (Task 4 Step 6 note.) The plan keeps `IterationResult(status="reject")` while passing commit status `"reset"`/`"repair_rollback"`. `run_job` reads `result.status` only via `format_reject`/`command_failed`/`rate_limited` (verified — `run_job` never branches on `result.status` string equality for set iters), so this is safe today, but it is fragile. The self-review asserts this; add an explicit regression test that a `reset` iter yields `result.status=="reject"` AND produces a champion-restore commit, so the decoupling is pinned.

**Minor**

- **M1 — `_init_repo` is `-> None`; the doc-existence test edits must not assume a return.** Task 4 Step 1 edits `_init_repo`'s gitignore/add only — fine. But note the phase2-3 plan (separate doc) wrongly treats `_init_repo` as returning the root; if any phase1.5 test is copied from there, it will break. Keep phase1.5's tests using `tmp_path` directly (they do).
- **M2 — Doc-consistency guard risk.** Task 6 mentions `tests/test_doc_consistency.py` "if it asserts a `.gitignore` invariant." Confirm whether such a test exists before relying on the conditional; if it does and pins `runs/*`, Task 4's flip will fail the suite. (I did not find it, but the plan should verify, not hedge.)

## Plan 2 — Phase 2+3 (worktree / parallel / gated promotion) — **needs-rework**

### Strengths

- **The central design is correct and well-motivated.** Per-job worktrees cut from a protected `champion` (never a runner `repo_root`), promotion pulled out of the hot path into a serialized lane, and `fcntl.flock` + live-champion re-validation + `git update-ref` CAS together **do** kill the A-vs-B concurrent-beat race. The three-layer guard (lock serializes; re-validate catches a peer who promoted lower while we queued; CAS catches a ref move between read and write) is sound and appropriately belt-and-suspenders for a solo local operator.
- **Worktree isolation is sound.** `champion` is never checked out by a runner; each job is `git worktree add -b job/<id> champion`; `restore_lineage_head` targets the worktree's own HEAD while `reset` still restores from `champion`. The repair→lineage-head vs reset→champion split is the right correction for the worktree model.
- **The promotion splice (commit-tree off champion's tree, overlaying only `transcribe.py`'s blob via a temp `GIT_INDEX_FILE`) is a correct, worktree-free way to keep `champion` linear and metadata-free** — and it makes the plan genuinely independent of whether phase1.5 has landed (the splice discards job-branch metadata commits either way). Good.
- **Grounding of the Phase-1 inventory is largely accurate:** `RunnerConfig` frozen at `:221`; `_run_git`/`gitops._git` both return `CompletedProcess` and thread `cwd=repo_root`; the unguarded promote arm at `runner.py:2236-2279`; `advance_champion_ref` at promote (`:2277-2279`); `ensure_champion_ref` in `run_job` (`:2286-2288`); `_decide_iteration` set override (`:1215`); the set scored `repair`/`reset` block (`:2249-2254`). The refine-parent wart description matches.

### Issues

**Critical**

- **C1 — Every worktree integration test calls `main = _init_repo(tmp_path)`, but `_init_repo` returns `None`** (`tests/test_harness_runner.py:58`, `-> None`). Tasks 2 and the launcher test, the refine-parent test, and the doc's own examples all do `main = _init_repo(tmp_path); gitops.ensure_champion_ref(main, ...)` — `main` is `None`, so `ensure_champion_ref(None, ...)` and `prepare_job_worktree(main, ...)` crash. The plan also claims "`_init_repo` already creates `champion` per phase1" (Task 1 note / Task 2 Step 1) — it does **not**; `_init_repo` creates no `champion` ref (verified). *Fix:* either change `_init_repo` to return the root and create `champion`, or have each test use `tmp_path` and call `ensure_champion_ref(tmp_path, ...)`. As written, none of the new tests run. This is pervasive across Tasks 1-3.
- **C2 — The promote-arm rewrite (Task 3-4) is under-specified to the point of being non-implementable as written, and contains undefined symbols.** It references `promo` and `verify_result.report` and `noise`/`baseline`/`cand_cer` (OK, those exist in scope at `runner.py:2219-2229`) but introduces `_reopen_as_refine(t, cand_cer, hyp_id)` ("helper below") whose body is **truncated/never completed** in the plan, and a `_main_repo_root` helper that derives the main repo from `git rev-parse --git-common-dir`. The "LOST race → reopen the closed set as refine" path mutates `t` (a frozen `Transition`) after `step_set` already closed the set on `promote`; this re-opens a `closed`→`refine` transition that the pure state machine never produces, bypassing `step_set`'s invariants. This needs a real design: `step_set` should model "promotion attempted but lost" as a first-class outcome (e.g. feed `beats_champion=False` and let it `advance` as a lineage head), not an ad-hoc post-hoc `replace()`. As written, Task 3-4 cannot be implemented without inventing the missing helper and is likely to corrupt set state.

**Important**

- **I1 — The "Phase 1.5 may or may not have landed" framing understates a real ordering hazard for the lock path.** The promotion lock file is `<repo_root>/.git/champion_promote.lock` (in the **main** repo's `.git`). In a worktree, `.git` is a *file* pointing at `<main>/.git/worktrees/<wt>`, and `repo_root` passed to `try_promote` is explicitly the **main repo** (`_main_repo_root`). Good — but the runner must pass the main repo, and `_main_repo_root` parsing of `--git-common-dir` must be tested (it returns a path relative to the worktree; the plan's `.parent if name == ".git"` logic is brittle for the common `.git` vs `.git/worktrees/...` cases). Add a direct test that `_main_repo_root(worktree_config)` resolves to the dir containing `refs/heads/champion`.
- **I2 — `live_champion_cer` reads `promotion_map.jsonl` from `repo_root/summary_dir`, but the map is written there too — across parallel jobs in separate worktrees this file must live in ONE shared location.** The plan writes/reads it under the main repo's `runs/_summary/` (correct, since `try_promote` takes the main repo). But each job *also* writes its own `runs/_summary/<job>_*` in its worktree. The plan must state that `promotion_map.jsonl` is the **main-repo** copy, distinct from per-worktree summaries, and that `live_champion_cer` must read the main-repo one. Otherwise re-validation reads a stale per-worktree map and the A-vs-B race re-opens. Currently the distinction is implied, not enforced; add a test with two worktrees confirming the map is the shared main-repo file.
- **I3 — Re-validation uses `decide_promotion(champion_cer=live)` where `live` is the lowest CER from the map, but the bootstrap champion (no promotions yet) returns `live=None`.** `decide_promotion(champion_cer=None)` treats "no champion" as "first candidate always wins" (verified: `decide_candidate` with `best_cer=None` keeps). So the FIRST parallel promotion always succeeds even if the committed `champion` ref already encodes a baseline CER better than the candidate. The live CER must fall back to the champion commit's recorded score, not `None`, when the map is empty. The plan mentions "or `champion`'s committed score" in prose (Design step 2) but `live_champion_cer` only reads the map. *Fix:* implement the committed-score fallback, or seed `promotion_map.jsonl` with the bootstrap baseline at `ensure_champion_ref` time.

**Minor**

- **M1 — `pytestmark` marker usage precedes marker registration.** Tests use `pytest.mark.worktree`/`promotion` (Task 1-3) but markers are only registered in Task 4 (`pyproject.toml`). Until then pytest emits `PytestUnknownMarkWarning` (and fails under `-W error`). Reorder: register markers first, or note the warning is benign. Minor but the plan claims clean test runs.
- **M2 — `cleanup_worktree` preserves the `job/<id>` branch but `prepare_job_worktree` re-links an existing branch's worktree without resetting it** — correct for resume, but two jobs with the same `job_id` (operator error) would collide on one branch/worktree silently. A guard or doc note would help. Minor for a solo operator.

### Consistency between the two plans

- **The dependency direction is stated, but the interaction with `commit_iteration`'s new status set is not reconciled.** Phase 2-3 (lines 31, 44-47) assumes `commit_iteration` commits code+metadata and `runs/_summary/` is git-tracked; phase1.5 changes both. The phase2-3 plan correctly argues the **promotion splice insulates `champion`** either way, so champion history is unaffected. **But** phase1.5 adds the commit statuses `"reset"`/`"repair_rollback"` and removes the F2 abort-commits, and phase2-3's Task 2-3/3-4 rewrite the *same* set `repair`/`reset` blocks and the promote arm. If phase1.5 lands first, phase2-3's edits to `runner.py:2249-2254` and the verify-fail block must be re-based onto phase1.5's already-modified versions of those exact lines (which now set `"reset"`/`"repair_rollback"` commit statuses, not `"reject"`). The plans touch the **same lines** with **different intents** and neither states the merge resolution. *Fix:* add an explicit "if phase1.5 has landed, the set `repair`/`reset` commit-status split is already done; this task only adds the `restore_lineage_head` call" note to phase2-3 Task 2-3, and the same for the promote arm vs phase1.5's code-only commit.
- Champion-ref semantics (`champion` branch, `ensure_champion_ref` idempotent, `advance_champion_ref`/`restore_file_from_ref`) are consistent across both plans and match `harness/gitops.py`.

### Scope discipline

- Phase 2-3 is at the **upper bound** of reasonable scope for a solo local harness: 5 new files, 5 new test files, a Popen pool, markers, and `git archive` packaging (Task 5) in one "coherent unit." The packaging (Task 5, `package_source.py` + `.gitattributes`) and the markers (Task 4) are **not load-bearing for the promotion-race fix** and could be split into a Phase 4 to shrink the blast radius. The parallel launcher + gated promotion (Tasks 1-3) is the coherent core; Tasks 4-5 are bolt-ons. Recommend splitting.
- Phase 1.5 scope is appropriate and minimal.
